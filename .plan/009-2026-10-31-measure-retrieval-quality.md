## Goal

An admin starts an eval run at `/eval-run` and reads recall@5, @10 and @20, MRR and nDCG@10 for hybrid search and for each half of it alone, over labelled eval cases, stored per run and per case; a non-admin cannot. That closes the retrieval half of AC08, which QA reports as half met until the correctness task, and AC01 stays green. The paid run gives plan 005's two open items their evidence: recall@k on a real corpus, and whether any cosine cutoff separates a relevant hit from the best hit of a question the corpus cannot answer. Nothing ranks differently after this task.

## Scope

- In:

- Out:

  - A cosine cutoff, a BM25 extension or a local embedding model: the evals decide each, and any change is its own plan. V07 records whether the two groups separate, and `.doc/conventions.md › Tooling` leaves the other two to the `keyword` rows. Proposed only if the groups separate: `- [ ] search drops semantic hits under a cosine cutoff`.

The correctness task's model calls change that sum, so that plan decides. Proposed: `- [ ] starting an eval run is rate limited per admin`.

## Assumptions

- A label cannot be a chunk id, because every index mints new ones (`_store`), so an expected chunk is `{ path, startLine, endLine }` at a pinned commit, and a case runs only against a `ready` source whose `indexed_commit` equals it; relevance is binary, because graded labels would need the judge.
- A run calls `search_knowledge_base(text=, limit=)` in `api/search/controller.py`, the rule the agent will use, never `GET /api/search`: `search_limit` is a route dependency (`api/search/routes.py`), so the rule stays unlimited by it, and through the route plan 006's 5 a minute would stretch 40 cases to 8 minutes, lock the admin out of `/search`, and refuse the hit limit, whose maximum there is 20. It asks for `EVAL.hit_limit`, 150, the whole union of three searches of 50, so one search gives each half's own top 20 with no new query.
- A run has `index_source`'s shape (`api/source/controller.py`): a `queued` row, a bus reaction, a conditional claim, one end on every exit, a boot sweep. One at a time by a partial unique index, whose 23505 the error handler already answers 409. All or nothing: one failed search fails the run with no scores, because a mean over fewer cases does not compare.
- A run stores ranks, cosines, its questions, its corpus and its settings, never a hit's content: a re-seed or a change to `SEARCH` must not rewrite what a stored run means, and repository text stays out of `eval_run`.
- Cases arrive through `infra/scripts/seed_eval_case.py`, the home the layer map reserves for seed, from a versioned JSON file, the more inspectable source; each question is validated as `SearchQuery` validates `q`, which `search_knowledge_base` requires of its caller.
- Only an admin's click starts a paid run, and no retry ever does. The start is a mutation in a click handler with `retry: false` (`main.tsx`) and `networkMode: 'always'`, because a mutation paused offline resumes by itself on reconnect (`QueryClient.mount`). No loader or query sends it, so `Try again` (`useSiteRetry` re-runs loaders), focus and reconnect only read; the client's one retry after a 401 re-sends a start the gate refused; a `failed` row offers no re-run, and the sweep ends a lost run and never requeues it. Every read here is free, so the 30 s default stands, not the search's `staleTime: Infinity`, and a failed start is a toast, so the group's boundary is true and no segment `error.tsx` is needed.

## Contract

| Endpoint | Request | Response | Errors |
| --- | --- | --- | --- |
| `POST /api/eval-run` | none | 201 `EvalRun`, `queued` | 401, 403, 409 (a run is active), 500 |
| `GET /api/eval-run` | `query.cursor?`, `query.limit?` | 200 `EvalRunPage { items: EvalRun[], nextCursor }`, newest first | 400, 401, 403, 500 |
| `GET /api/eval-run/{id}` | `params.id` | 200 `EvalRunDetail` | 400, 401, 403, 404, 500 |

- `EvalRun { id, status: 'queued'|'running'|'completed'|'failed', errorCode: 'no_runnable_case'|'search_unavailable'|'interrupted'|'internal'|null, caseCount, skippedCaseCount, incompleteCaseCount, headline: EvalScore|null, createdAt, updatedAt }`. `headline` is the `hybrid` `all` row.
- `EvalRunDetail` is `EvalRun` plus `scores: EvalScore[]`, `cases: EvalCaseResult[]`, `corpus: { url, ref, indexedCommit, chunkCount }[]`, `settings: { embeddingModel, rrfK, candidates, keywordCandidates, trigramThreshold }|null` and `cosine: { relevantMin, relevantMedian, noAnswerMedian, noAnswerMax }|null`, each of those four a number or null. `corpus` is empty and `settings` null until a run starts; until it completes, `scores` and `cases` are empty and `cosine` is null.
- `EvalScore { search: 'hybrid'|'semantic'|'keyword', kind: 'all'|'identifier'|'paraphrase', caseCount, recallAt5, recallAt10, recallAt20, mrr, ndcgAt10 }`, each score 0 to 1; a row with no case is absent. `hybrid` is the order returned, `semantic` orders by `semantic_rank`, `keyword` by the RRF sum of `full_text_rank` and `trigram_rank` alone.
- `EvalCaseResult { question, kind: 'identifier'|'paraphrase'|'no_answer', skipReason: 'source_missing'|'expected_chunk_missing'|null, incomplete, rank, recallAt5, recallAt10, recallAt20, reciprocalRank, ndcgAt10, topCosine, relevantCosine }`; the last eight are numbers or null, and null for a skipped case. `rank` is `hybrid`'s first relevant rank in the top 20. A `no_answer` case has only `topCosine`, the cosine of the semantic search's first hit; `relevantCosine` is that of the best-ranked relevant hit.
- Relevant: a hit from a source at the case's commit, on the same path, sharing at least half of the shorter of the two line ranges. Over the first `k` hits, recall@k is the share of expected chunks with a relevant hit; reciprocal rank is 1 over the first relevant rank in the top 20, else 0; DCG adds `1 / log2(rank + 1)` at a hit that is the first for its expected chunk, and nDCG@k divides by the DCG of `min(expected, k)` such hits. A score is the mean over scored cases; `no_answer` cases enter no mean, only `cosine`.

## Risks

- 30 answerable cases are a small sample: recall@5 of 0.7 has a 95% interval of about ±0.16, so a difference under 0.2 between searches or runs means nothing — the record says so, and the file can grow with no code change.
- Labels written by the agent reading the code leak its words into the question, which flatters keyword search — `identifier` and `paraphrase` report apart, `check_eval_cases` holds a paraphrase to no shared identifier, and the user reads the file before the paid run.
- A cutoff guessed from intuition would be wrong: V08 of plan 005 saw a relevant chunk at cosine 0.2435, so even 0.3 drops it, and one repository's numbers say little about another language — hence `no_answer` cases; a cutoff is proposed only if `noAnswerMax` sits under `relevantMin`, and it would apply to the semantic half alone, since a keyword match has no meaningful cosine.
- A score depends on what else is `ready`, because a search has no filter by source (plan 005) — each run stores its `corpus`, and only runs on one corpus compare. An index running beside a run can cut a search short, which the count and `Alert` show.
- A line number holds at one commit only — a case is pinned to it, a moved source skips the case visibly instead of scoring it 0, and a span no chunk matches is `expected_chunk_missing`, so a bad label is never read as bad retrieval. The half-of-the-shorter rule is generous to a large chunk, a class of 100 lines matching a label of 10: it measures whether the chunk holding the answer ranks, which is what a reader or the agent receives.
- Plan 006's window does not reach a run, by design, so a run is the one unmetered path to `search_knowledge_base` until the agent's — it needs the admin role and the one active slot, spends only what 200 seeded cases can, and holds one of ten pooled connections at a time, each statement under the 3 s limit. `embed_query` never waits out a 429, so a throttle fails the run, but cases run one by one, far below tier 1's 2,000 requests a minute.
- Plan 006's bar stands, neither lifted nor raised here: the app stays unreachable from outside until `search has a global spend cap` and `concurrent searches are capped below the pool size` land, and both are queued after this task — only `grant_admin` makes an admin, so open sign-up multiplies nothing a run spends. Neither cap exists yet, so a run's embeddings and pool slot count toward nothing, and each of those plans must say whether a run counts, because a cap inside the rule meets its searches too.
