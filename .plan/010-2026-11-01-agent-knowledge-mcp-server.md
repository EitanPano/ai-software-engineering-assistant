## Goal

A person asks the agent about connected code and the agent decides to search the knowledge base through our own `knowledge` MCP server, searches again when a first result does not answer, and answers citing file and line, or says the knowledge base holds no answer; each search shows as it happens and is stored as a tool call. That closes AC04, its judgement clauses on real-key evidence (V07), the `knowledge` half of AC05, which QA reports as half met until the GitHub task, and AC06's last clause, a tool with no policy is denied; AC01 stays green. It is the first task to offer the real model a tool, so it ships the policy check in the loop and the bound on a caller plan 006's limit does not reach.

## Assumptions

- What bounds this caller, since `search_limit` is a route dependency that never reaches it: the loop spends at most `AGENT_TOOL_CALLS_PER_RUN`, 12, counted from `tool_call` rows so an approval's resume keeps the count, and `message_per_user` multiplies that; `knowledge` runs `KNOWLEDGE.concurrent_searches`, 4, below its own pool of 10, and refuses past `slot_wait_seconds`, 5; the tool takes no `limit`, so an answer is at most `hit_limit`, 10, in `output_max_chars`, 18,000, under the loop's cut; and only the loop can reach it (Question 2).

- Every run lists each enabled server and stores the last good listing on its `mcp_server` row, so a new conversation offers tools from those rows and an outage changes no request. The model sees `<server>__<tool>`; the policy is read at each call, so a stored definition never outranks it.

## Contract

| Endpoint | Request | Response | Errors |
| --- | --- | --- | --- |
| `GET /api/run/{id}/event` | unchanged | `RunEvent` gains `McpServerUnavailableEvent { type: 'mcp_server_unavailable', sequence, createdAt, name }`, at most one per server per run; the run goes on. `RunErrorCode` and `ToolCallStatus` do not change: a search that fails is `failed`, a refused one `denied` | unchanged |

- `knowledge`, outside `openapi.json`: `POST /mcp` on Streamable HTTP with `Authorization: Bearer <KNOWLEDGE_MCP_TOKEN>`, else 401; `GET /health` 200, no token and no store. The model sees the tool as `knowledge__search`.
- `search` takes `{ query: string }`, `required`, `additionalProperties: false`, no `limit` and no length keywords, because `strict` refuses `minimum` and `maxLength`; the server checks `query` as `SearchQuery` checks `q`.
- Its result is one text block of JSON: `{ hits: [{ url, ref, path, symbol, startLine, endLine, content }], incomplete, omitted }`, best first, whole hits only, `omitted` counting those that did not fit. It is mapped field by field, so plan 009's `SearchHitRecord.cosine`, `score` and the ranks stay out. No hits is a success, not an error.
- A failure is `isError` with one fixed code, never exception text: `invalid_query`, `busy`, `search_unavailable`.

## Risks

- One account's rate: 2,880 sends a day at 12 calls is at most 34,560 searches, an estimated $0.71 a day at 170 tokens each and $2.07 at 500, against `/search`'s $0.15 — accepted, because the same runs' model calls cost far more, and no window of its own, because `search_per_user` would stop an honest run at its sixth search and lock its owner out of `/search`. Accounts multiply it, so plan 006's bar stands: the app stays unreachable from outside until `search has a global spend cap` lands, and that plan must say whether this path counts. A burst waits on `knowledge`'s slots, then fails `busy`, and never reaches the API's pool, because `knowledge` has its own.
- A run's results can add 12 × 18,000 = 216,000 characters to its prompt, about 60,000 tokens and $0.24 on an uncached call, repeated in the history — `AGENT_MAX_TURNS` and the budget bound it, and `agent runs have a spend cap` stays queued.
- The SDK is unread at planning time and its 1.x and 2.x differ — the last Assumption's report comes before anything builds on it, and it may change `use_client` or `serve`, which the driver records.
- A failure inside a session's task group can cancel what holds it — one task per operation keeps it off the run, and V02 proves a shutdown's cancellation still reaches `execute_run`.
- Repository text can steer `query` — it travels in tool results only, the tool only reads, and the policy runs at each call; what a query carries goes to Voyage, which `.doc/product-definition.md` discloses.
- Plan 009 found no cosine that separates the groups (`noAnswerMax` 0.369 above `relevantMin` 0.189, the top no-answer questions near the domain), so a near-domain question gets plausible hits and the model alone must admit no answer, and the fake can drift from the real wire — `request_problem` refuses what the skill's schema limits name, and V07 is the only evidence for either until the correctness evals.
- A conversation whose first run falls in `knowledge`'s first-ever outage, with no listing stored yet, stores no tools and keeps none: A never adds them, and Question 1's C would meet there the shape it leaves unproven — accepted: the run reports it, and the next conversation after a good listing has them.

## Rollback

Removing them is a human's: drop `tool_call`, `tool_policy`, `mcp_server` and the two `conversation` columns, then delete the file's `schema_migration` row.
