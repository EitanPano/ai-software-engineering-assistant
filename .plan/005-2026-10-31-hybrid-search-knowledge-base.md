## Goal

Any signed-in user searches the chunks of every `ready` source from `/search` and gets the best chunks with their repository, file and line range. Semantic, full-text and trigram search run over `chunk`, and RRF fuses them in one SQL statement. AC03 closes here: on the fixture repository an exact identifier and a paraphrase each return the expected chunk in the top 5, and AC01 stays green. The agent gets no search tool yet.

## Scope

- In:
  - `GET /api/search`, and a controller rule the `knowledge` MCP task can call.
  - The `chunk.keyword` column, `pg_trgm` and the search indexes plan 004 left to this task.
  - `/search`, with the text in the URL so a reload or the back button keeps the results.
  - `incomplete` on a result a scan limit or a candidate cap cut short, so no limit fails silently.
- Out:
  - Paging, a filter by source, highlighting and a link to GitHub: AC03 asks for none of them.
  - A similarity cutoff: a threshold needs evidence, which `admin can measure retrieval quality with an eval run` produces.
  - The agent's tool: `agent searches the knowledge base through our MCP server`.
  - A keyword-only answer while Voyage is down: a result that silently lost its semantic half cannot be inspected, so it is a 503.
  - A limit per user, proposed: `- [ ] search is rate limited per user` (Question 2).

## Contract

| Endpoint | Request | Response | Errors |
| --- | --- | --- | --- |
| `GET /api/search` | `query.q: string`, 1 to 500 characters after trimming, no NUL; `query.limit?: integer`, 1 to 20, default 10 | 200 `SearchResult { items: SearchHit[], incomplete: boolean }`, best first; `items` is empty when no `ready` source holds a chunk | 400, 401, 503 (Voyage unreachable or limiting, or the search passed its statement limit) |

- `SearchHit { chunkId, sourceId, url, ref, path, symbol: string | null, startLine, endLine, content, score, semanticRank: integer | null, fullTextRank: integer | null, trigramRank: integer | null }`.
- `url` and `ref` are the source's. `startLine` and `endLine` are the chunk's stored range, as GitHub numbers lines: a piece of a line over 6,000 characters has one number, so two hits can share a range and only `chunkId` identifies a hit. `symbol` is null for a line window and for a name plan 004 dropped.
- A rank is the chunk's position in that search, 1 is best, and `null` means that search did not return it. `score` is the sum over the three of `1 / (60 + rank)`.
- `incomplete` is true when a keyword search reached `keyword_candidates`, or the semantic search found fewer chunks than `ready` sources could supply. Nothing else sets it.
- A search is a bounded top-k, not a list: a cursor would re-embed the text and re-fuse a ranking that can shift, so `api-design`'s `nextCursor` does not apply.

## UX

- /search — list — search the knowledge base — states: loading `ListSkeleton` where the results go, the form staying on screen · empty `EmptyState` before a search, and one saying nothing matched after a search with no hit · error the group's `ErrorState`; an `incomplete` result shows an `Alert` above the hits — tone: calm, dense, precise — phone: one column, the form above the results, code wrapping rather than scrolling sideways

3. `backend/src/app/api/search/schema.py`, `routes.py`, `backend/src/app/config/routes.py`, `backend/src/app/openapi.py`, `backend/openapi.json`, `backend/tests/test_openapi.py` — contract stage: `require_auth`, `SearchHit` and `SearchResult` in `COMPONENTS`, the path in `TestTheDocument::test_documents_exactly_the_surviving_paths` and the names in `TestTheShaping::test_makes_a_component_of_exactly_the_listed_names`, then `contract`.
4. `backend/src/app/services/voyage.py` — paid, $0.12 per million tokens, about $0.00002 a search: `embed_query` with `input_type: query` (per Voyage's API reference on 2026-10-31, a query gets its own retrieval prompt), the same `output_dimension`, `truncation: false` and `_vectors`' checks; `_embed` takes a budget, because the index's 4 attempts of 60 s could hold a request for 4 minutes and `error-handling` allows a request path 3 attempts. On a 429 the index path waits what `Retry-After` says, at most 2 minutes, or about a minute with no usable header, because its backoff of 3.5 s cannot outlast a per-minute limit and a failed index re-embeds everything; the request path keeps its short budget and answers 503.
5. `backend/src/app/api/source/service.py` — `prepare_search` (for the transaction: `hnsw.iterative_scan = strict_order`, `hnsw.max_scan_tuples`, `pg_trgm.word_similarity_threshold`), `count_ready_chunks` (the sum of `source.chunk_count`) and `search_chunks`: one statement of three ranked searches over `ready` sources only, each keyword search ranking at most `keyword_candidates` matches, fused by RRF with ties broken on `chunk.id`, and reporting how many chunks each search found; a null trigram token matches nothing.

7. `backend/src/app/api/search/controller.py` — the rule `search_knowledge_base`: embeds outside any transaction, so a slow Voyage call holds no pooled connection; passes the trigram token only when `q` is one word of `trigram_min_chars` to `trigram_max_chars`, because a two-letter word has no trigram of its own, only padded ones, and on real code `re` made half the chunks candidates; turns `EmbeddingUnavailable` into `upstream_unavailable`. The `search` handler rechecks the caller and maps hits to the wire.
8. `backend/tests/fixture_repository.py`, `backend/tests/fake_voyage.py` — `src/limiter.py`, real code of about 600 lines, in `FIXTURE_FILES` and `INDEXED_PATHS`: a symbol over 4,000 characters, one over the 6,000-character bound, an identifier only a dotted call past line 300 holds, and one line over the bound; `KEYWORD_QUERY`, `DOTTED_QUERY`, `LONG_LINE_QUERY` and `SEMANTIC_QUERY` with the chunk each expects, the paraphrase sharing no lexeme with its chunk. `vector_of` becomes a dense SHA-256-seeded unit vector: with HNSW forced, one-hot vectors found the exact match 39 times in 100 and dense ones 100 (probed 2026-10-31). ## Risks

- A source still indexing can hide results: pgvector filters after the index scan (its README, checked 2026-10-31), and on 0.8.7 with 300 in-flight chunks nearest the query the default scan returned 0 of 8 `ready` chunks and `strict_order` all 8 — but a scan stops at 20,000 tuples or its `work_mem` share with no documented signal, and one source holds up to 100,000 chunks, so `incomplete` reports the shortfall; V04 and V06 pin it.
- A common word matches every chunk, and ranking 100,000 is unmeasured — each keyword search ranks at most 2,000 matches, so a very common word's order is arbitrary among those and the result says `incomplete`; the 0.9 threshold keeps an identifier's near matches from filling that cap; V06 is the first measurement.
- The planner sizes `ready` chunks by the share of sources that are `ready`, not by their chunks: beside one `ready` source of 100,000 chunks and fresh statistics, 49 `failed` sources kept a trigram search at 18 ms and 69 took it to 8 s (measured 2026-10-31) — the result is right but slow, and under 2% of sources `ready` is out of reach for v1, so it is accepted.
- With fresh statistics, a source still indexing can hide a smaller `ready` one: the planner counts one `ready` source of two as half the chunks and scans HNSW, so with 100,000 chunks `indexing`, a far `ready` source of 8 returned 1 hit in 145 ms with `incomplete` true and logged — the same search took 7 ms and found all 8 before the refresh, only because the planner had read every chunk's document. Accepted: it ends with that index, `incomplete` reports it, and V06 pins it.
- `limit` counts matches, not rechecks, and `<%` runs on every GIN candidate before the `ready` filter, so one word can cost `word_similarity` on every chunk of a source still indexing — `statement_timeout_ms` bounds it at 3 s, below the pool's 5 s acquire wait, so such a search answers 503 rather than holding one of 10 connections. A word that hits the limit fails again on every retry until the index ends, the 503 replaces the page and its form, and about 34,000 candidates are enough, so a repository where a word is in every chunk reaches it at a third of the ceiling. A word under 3 characters runs no trigram search, so `re` misses a dotted `self.re(x)`, with `incomplete` false. V06 measures these shapes. Accepted by the user at the commit gate (2026-10-31), so step (4) of review.md's P1 stays closed: while a very large source indexes, that search answers a 503 on every retry until the index ends.
- A top 5 is a low bar on a small fixture, and with no cutoff every query returns its nearest chunks even when none is relevant — step 8 grows the fixture past 27 chunks; recall@k and the cutoff are the eval task's.
- `0006`'s indexes make every chunk insert in `index_source` slower and add disk per source, unmeasured at the ceiling — it is a background task that commits every 512 chunks, so chat waits on nothing, and V06 prints the rate and sizes.
- Repository text, paths and symbols are attacker-controlled and reach every user's browser here for the first time, read back from `chunk` as untrusted as when they arrived — they render as text with bidi and control characters shown, never as links or Markdown, and the backend logs none of them; V07 proves it.
