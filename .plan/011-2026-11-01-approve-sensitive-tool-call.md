## Goal

A tool call whose `tool_policy` says `ask` stops its run at `awaiting_approval` with no process waiting, shows the person its exact arguments in place in the conversation, and runs only after they approve; a rejection reaches the agent as a denied result and the run goes on; a pending approval survives a server restart. That closes AC06's remaining clauses. No tool ships at `ask` here: `knowledge__search` stays `allow`, so the journey runs on a test server's tool, and the first real one is the GitHub task's.

## Assumptions

- The pause keeps `response.content` whole and the results already known in `run.pending_turn`, not in `message`: `append_turns` promises a served `tool_use` its result and history is never edited, so an unanswered turn left in `message` by a crash would fail every later send. Only `served_blocks` are asked or answered; a `tool_use` before the final `fallback` is stored, never run, and dropped by `echo_blocks` at send, as in a turn never paused. A followed run replays its text from `run_event` until the resume stores the turn.
- `approval` is queried by `api/run/service.py`, as `search` reads `source`'s chunks, and `api/approval/` holds routes, schema and controller only: a pause and a last decision must each commit rows, events and status together, a cross-module flow is not atomic (`backend/AGENTS.md`), and a half-written decision would leave a run with no way forward.
- The sweep keeps listing `queued` and `running`, so a pending approval is untouched; the last decision flips the run to `running` in its own transaction, so a crash from there ends it `interrupted` (`.doc/architecture.md`, item 8), nothing restarts it, and each approved call runs at most once.
- Binding is `approval.arguments_digest`, SHA-256 of the canonical stored `arguments`, sent in the event, echoed by the decision and compared again at execution before `_run_tool`'s own gates (enabled server, `find_effect`, offered in the frozen prefix, schema), so a later `deny`, a disabled server or a changed row denies; the echo is one field and makes a decision name what the client was shown, not only an id.
- In a mixed turn the other calls run at once and their results wait, so no search is held for a human; an `ask` call that fails a gate, or sits past the budget by position, is answered with no question and stored as `_Call` says; `count_tool_calls` counts every row, pending and denied ones too, and `AGENT_MAX_TURNS` counts the run's stored assistant turns, so a resume keeps both; a send during a pause stays the 409, because each served `tool_use` needs its `tool_result` in the next user turn.
- Verified in the `claude-api` skill (`shared/model-migration.md`, preserved thinking): a signature binds `system`, the set of `tools`, every earlier message and a chain to the previous thinking block, and `max_tokens`, `output_config` and `cache_control` sit outside it, so one appended `tool_result` turn after the unchanged assistant turn stays valid under `prefix_mismatch_behavior: "error"`; the skill states no age limit on a signature, which is absence and not a promise (Question 1); past the five-minute cache a resume is a cache miss, written at $5 per million, not an error; `stop_reason: pause_turn` is the server-tool stop and has nothing to do with this pause.

## Contract

| Endpoint | Request | Response | Errors |
| --- | --- | --- | --- |
| `POST /api/approval/{id}/decision` | `params.id: string`; `body: { decision: 'approved' \| 'rejected', argumentsDigest: string }`, 64 lowercase hex characters | 200 `Approval { id, toolUseId, decision, decidedAt }` | 400 `validation_failed`; 401 `unauthenticated`; 404 `not_found`, missing or another user's; 409 `conflict`, already decided, `argumentsDigest` differs, or the run no longer waits; 500 `internal` |
| `GET /api/run/{id}/event` | unchanged | `RunEvent` gains `ApprovalRequestedEvent { type: 'approval_requested', sequence, createdAt, approvalId, toolUseId, argumentsDigest }` and `ApprovalDecidedEvent { type: 'approval_decided', sequence, createdAt, approvalId, toolUseId, decision }`; the stream closes cleanly once a run at `awaiting_approval` has delivered its events | unchanged |
| `GET /api/conversation/{id}`, `POST /api/conversation/{id}/message` | unchanged | `Run.status` gains `awaiting_approval` | a send during a pause is the existing 409 `conflict` |

- An `ask` call's events are `tool_call_started`, whose `input` is what the person reads, then `approval_requested`; `tool_call_finished` follows the decision, `denied` on a rejection.
- `ToolCallStatusName`, `RunErrorCodeName` and `RunFinishedEvent.status` do not change.

## UX

- /conversation/:id — detail — approve or reject a waiting tool call, otherwise send a message — states: loading `CardSkeleton` · empty `EmptyState` above the send form · error the group's `ErrorState`; a waiting call is its tool row, in place in the log, with a status `Badge`, its whole arguments, approve filled and reject outline, and send stays off until the last decision; a stale decision is a toast in our words — tone: calm, dense, precise — phone: one column, both buttons full width, the arguments scrolling inside their own focusable box

## Risks

- No real tool asks until the GitHub task, so AC06 rests on a test server's tool — it goes through the real client, policy read and route, and that task inherits this path.
- A crash can end a run after an approved call ran, leaving its result out of the history — accepted: at most once beats twice for a write, the run ends `interrupted`, and a repeat by the model is a new approval.
- Repository text can steer the model toward a harmful call whose arguments read safely, which is why this gate exists — the arguments show whole, in plain text, with hidden characters escaped; nothing truncates them and nothing approves in bulk; a person can still click through, so policy stays the limit.
- A resume past the cache window writes the history again, about $0.30 at $5 per million for the 60,000 tokens plan 010 bounds — accepted: a 1-hour TTL would double every write for a rare case, and `agent runs have a spend cap` stays queued.
- A conversation cannot go on until its call is decided — accepted: rejecting is always open, and the expiry line is proposed.
- `LLM_MODEL` changed during a pause loses that reasoning — the API drops what the new model cannot read and the request succeeds (`claude-api` skill, model binding).
- Ending a server on Windows ends only the venv's launcher — the restart test stops the tree as `tests/services/test_parse.py` does and waits on `/api/health`.
