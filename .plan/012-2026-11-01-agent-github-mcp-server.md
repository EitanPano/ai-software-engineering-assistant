## Goal

A person asks the agent to read or change something on GitHub, and the agent calls GitHub's official MCP server beside our `knowledge` server: a read runs at once, and a write stops at plan 011's approval gate, so `github__add_issue_comment` and `github__issue_write` are the first real tools at `ask`. That closes AC05, whose GitHub half has been open since plan 010, and puts AC06 on a real tool; AC01 and AC02 stay green. It is the first third-party server, so `.doc/conventions.md › Agent security` applies for the first time: its definitions are pinned when an admin accepts them, a changed definition is denied, and the GitHub token never reaches the backend. An install with no GitHub token behaves as it does today. There is no public API change, so `openapi.json` and the generated client stay as they are.

## Scope

- In:
  - `github` as the second `mcp_server`: GitHub's image at `v2.0.3` in Compose, limited to seven tools, opt-in through profile `github`.
  - The GitHub gateway of Question 2, the only process that holds `GITHUB_MCP_PAT`.
  - The waiting tool row without its height cap: a GitHub write is the first long argument a person approves, and the row must show all of it.
  - The pin: `mcp_server.pinned_tool_definition`, the admin's `accept_mcp_server` command, tools offered from the pin, a deny on a changed definition.
  - What a real server needs of our client: listing before a call, reading an embedded file, no `strict` on a third-party tool.
  - A free live check, and the paid smoke of Question 1.
- Out:
  - Routes and screens: `admin can manage MCP servers and tool policy`, which wraps `accept_listing` and shows the change before an admin accepts it.
  - Later tools in existing conversations: Question 3. In the backlog: `- [ ] a tool accepted later reaches existing conversations`.
  - Code changes (`create_branch`, `push_files`, `create_pull_request`): a push puts whole files in an approval, which needs a review view no AC asks for. In the backlog: `- [ ] agent proposes a code change as a GitHub pull request`.
  - Per-person credentials: one token acts for every account (see Risks). In the backlog: `- [ ] each user acts on GitHub with their own token`.
  - Indexing private repositories: `admin can connect a private GitHub repository`; `services/github.py` stays anonymous.

## Assumptions

- Read at tag `v2.0.3`, released 2026-10-21 (`cmd/github-mcp-server/main.go`, `pkg/http/`, `pkg/github/repositories.go`, `pkg/github/__toolsnaps__`): `github-mcp-server http` serves stateless Streamable HTTP at `/` on 8082; `GITHUB_TOOLS` limits the list and a bad name stops the boot; `GITHUB_LOCKDOWN_MODE` withholds public content by authors without push access, best effort, so it stays on, and the README says that most issues on another project's public repository then read as restricted; `get_file_contents` returns a file as an embedded resource, which today's `call_tool` drops, keeping only the line that says it succeeded. The image's digest is read at the backend stage, because `gh` here lacks `read:packages`.
- The pin: `pinned_tool_definition` holds what an admin accepted and `tool_definition` stays the last listing. Every server but `knowledge` offers only pinned tools whose live listing matches, the pin itself while the server is down, so an outage changes no request and no conversation freezes short, and nothing while the pin is null. The model reads only pinned text, so a changed description cannot reach it.
- A changed definition denies at three points, by equality of name, description and schema: discovery stops offering it; `_run_tool` denies before any `ask` when the last listing or the conversation's frozen definition differs from the pin; and `call_tool` lists again in the call's own session and calls nothing on a difference, which catches a change during a long approval. That listing is needed anyway: `mcp` 2.3.0 negotiates protocol `2026-07-28`, where a server refuses a call whose `x-mcp-header` arguments lack their `Mcp-Param-*` headers, and the client writes them only for a tool that session listed (`mcp/client/session.py`).
- Without screens, `accept_mcp_server <name>` is the admin's act, as `grant_admin` made the first admin: it prints the live listing whole, its digest and what changed from the pin, takes a yes, stores exactly what it printed and enables the row, in Compose through `backend-migrate`. `0011` seeds `github` disabled with its `tool_policy` rows, so nothing is listed until a person accepts, and no policy is edited by hand.
- `strict` stays on `knowledge` only, which changes `.doc/conventions.md`'s Structured outputs row, as that file allows: `strict` needs `additionalProperties: false` on every object and refuses `minimum`, `maximum` and `minLength`; none of the seven closes its top-level object and six use one of those keywords, so a strict definition would be a 400 on every request, and rewriting a schema would send what no admin accepted and the server does not hold. `validate_input` already checks every input against the full schema, and a failure costs one turn.
- Seven tools, 13,662 characters, about 4,200 tokens: reads at `allow` (`get_file_contents`, `issue_read`, `list_issues`, `pull_request_read`, `list_pull_requests`), writes at `ask` (`issue_write`, `add_issue_comment`). That is about $0.02 written once a conversation and $0.0008 a call cached; the default toolsets cost several times that and list writes no policy row covers.

## Risks

- One token acts for every account and a `user` approves their own calls (`.doc/product-definition.md`), while `register` takes any address, so anyone who signs up can read wherever the token reaches with no click, and write there with only their own — accepted for local use (the user, 2026-11-01): the README asks for a fine-grained PAT on named repositories with the least permissions and names this on its public-host list, plan 006's bar stands (the app stays unreachable from outside), and the per-person line is in the backlog.
- Repository and issue text can steer a write whose arguments read safely — every write is `ask` with its whole arguments in view, and tool output stays data; lockdown mode is a best-effort filter, not a boundary.
- The gateway is new code holding a write token — one path, one method, an allow-list of headers, no logged header, a 401 before anything forwards; the review treats it as a new auth boundary.
- `x-mcp-header` is a keyword the API may refuse outside `strict` — all seven carry it on `owner` and `repo`; a refusal is free, `count_tokens` accepted them, and V08's first request settles it; the fallback is to leave `x-` keys out of what is sent, recorded by the driver.
- The fake can drift from the real server — recorded definitions, the SDK's own header check, `live_github.py` against the real listing, and V08.
- A new image digest can change definitions — every changed tool denies until an admin accepts again, by design, and `accept_mcp_server` prints what changed.
- A list before each call adds round trips — one session, bounded by `MCP.call_seconds`, and only for third-party servers.

## Rollback

Set `github` to `enabled = false` first: the old code reports an enabled row with no `url` as down on every run. Then revert the branch. A conversation frozen with `github__*` tools keeps its history valid and each such call fails as unavailable. `0011` adds a column the old code ignores, and the wider check is harmless. Removing them is a human's: delete the `github` `tool_policy` rows and its `mcp_server` row, drop the column, restore the check, then delete the file's `schema_migration` row.
